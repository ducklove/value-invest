# 구조 검토 후 개선 내역

2026-09-08. 구조 검토에서 재현한 데이터 일관성·출처 검증·수명주기 문제를
먼저 수정하고, 기존 기능의 API 계약과 화면 로딩을 보강했다.

## 적용한 개선

| 영역 | 이전 문제 | 적용한 동작 |
|---|---|---|
| SQLite 격리 | 다른 요청이 쓰기 도중의 미커밋 값을 읽을 수 있음 | 일반 조회와 쓰기 연결 분리, 쓰기는 기존 잠금으로 직렬화 |
| 복합 조회 | 조회 사이의 커밋으로 한 응답에 다른 시점이 섞일 수 있음 | 보유 목록·수익 분해·정산 화면 조회를 `read_snapshot()`으로 묶음 |
| 정산 기준 | 이전 총액과 이후 또는 더 오래된 종목 금액이 혼합될 수 있음 | 선택한 총액과 정확히 같은 날짜의 종목 금액 조회, 누락은 빈 값 유지 |
| 변경 요청 | CORS가 응답을 막아도 외부 출처의 로그아웃이 실행됨 | API 변경 요청의 Origin/Referer 검증, 출처 없는 세션 요청은 전용 헤더 요구 |
| 시작·종료 | 시작 도중 실패 시 연결 누수, 일부 작업은 취소만 하고 종료를 기다리지 않음 | `AsyncExitStack`으로 부분 시작도 정리, 작업 종료·취소 회수 후 DB 종료 |
| 운영 로그 | 비동기 기록이 DB 종료와 경합 | 기록 작업 추적과 종료 전 대기, 제한 시간 초과 시 취소·회수 |
| API 응답 | 핵심 데이터의 응답 스키마가 비어 있음 | 금액·시세·정산·수익 분해·논거 등 10개 작업에 응답 모델 적용 |
| 초기 화면 | 사용하지 않는 화면 파일과 대시보드 요청도 실행 | 11개 파일은 화면 진입 시 로드, 숨겨진 대시보드 초기 호출 제거 |
| 테스트 설정 | AI 기본 모델 이름 변경이 기능 테스트를 깨뜨림 | 고정 테스트 설정으로 등급과 실제 요청 모델의 연결 검증 |

## 개발 계약

- 일반 조회는 `get_db()`, 여러 SELECT의 시점 일치가 필요하면
  `async with read_snapshot():` 또는 `@read_snapshot()`을 사용한다.
  읽기 스냅샷 안에서 쓰기를 시작하면 오류가 발생한다. 같은 task의 중첩 읽기와
  쓰기 트랜잭션 내부 조회는 기존 연결을 재사용하며, 자식 task는 상속하지 않는다.
- 기본 조회 연결은 부트스트랩·테스트 시드 호환 때문에 쓰기 가능한 상태다.
  요청 중 쓰기는 반드시 `transaction()`을 사용한다. 임의의 직접 쓰기까지
  강제로 차단하는 구성은 아니다.
- 응답 모델의 알려진 금액에는 유한한 수만 허용한다. 시세 없음·null·자료 부족을
  0으로 보완하지 않는다. 일부 모델은 기존 확장 필드를 보존하는 점진적 계약이며,
  모든 API 필드를 엄격히 고정한 상태는 아니다.
- 허용 출처는 `CORS_ALLOWED_ORIGINS`에서 결정하며 Host·전달 헤더로 확장하지
  않는다. 환경변수를 지정하면 기본 출처 목록 전체를 대체하므로 실제 접속 출처를
  포트까지 포함해 등록한다. 브라우저 변경 요청은 공통 `apiFetch()`를 사용한다.
  출처 헤더가 없는 세션 요청은 `X-Requested-With: fetch`가 필요하다.
- Google 로그인 콜백은 자체 double-submit 검증을 유지한다. 쿠키 없는 CLI·기기
  요청은 기존 엔드포인트 인증을 유지한다. HTTPS 판단은 신뢰 프록시 처리가 끝난
  ASGI scheme을 사용한다.
- 정산 화면의 SQL은 `repositories/snapshots.py`, 계산·조합은
  `services/portfolio/snapshot_views.py`, 인증·응답은 라우터가 담당한다.

## 측정과 검증 범위

최종 검증: `python -m pytest -q` 1,392개 통과(기존 의존성 사용 중단 경고 2건),
`npm test` 370개 통과, `npm run test:e2e` 2개 통과,
`python -m ruff check .` 및 `git diff --check` 통과.
Python 검사는 `.venv-review` 환경에서 실행했다.

보유종목 초기 진입 기준 로컬 JS 요청 52 → 42개, 지연 파일 11개.
JS 원본 합계 약 935 KB → 773 KB, 약 17.3% 감소. `app-config.js`는 요청 수에
포함하고 동적으로 생성되는 응답 용량은 파일 합계에서 제외했다.
이는 gzip 전 파일 측정이며 CSS·외부 라이브러리·실제 기기 로딩 시간은 별도다.

임시 DB의 동시 쓰기·조회·롤백·취소, 실제 앱의 출처 검사·응답 직렬화,
부분 시작 실패·종료 정리, 지연 로더의 실행 순서·재시도·탭 경합을 검사한다.
브라우저 검사는 실제 인증·임시 DB와 고정 시장 데이터를 사용하는 테스트 앱으로
실행하며, 출처 검사 미들웨어도 포함한다. 실제 앱 수명주기는 별도 통합 검사에서
외부 어댑터만 대체해 검증한다. 운영 배포·실제 투자 데이터 변경은 포함하지 않는다.

## 후속 우선순위

1. 위키·관리자 라우터의 SQL과 긴 업무 로직을 저장소·서비스 계층으로 이동.
2. 나머지 API 응답 계약 확대, 선택적 확장 필드를 검증 가능한 명시적 모델로 전환.
3. 종목 분석·시장 대시보드의 전역 상태 의존을 줄인 뒤 화면별 지연 로딩 확대.
4. 백그라운드 업무 전체의 작업 등록을 공통화하고 실패·재시도 상태를 운영 화면에 연결.
5. 실제 브라우저의 압축 전송량·화면 준비 시간과 운영 DB 지연을 측정해 성능 예산 설정.
